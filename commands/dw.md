description: Run a multi-agent team in the background. Role agents (PM, Architect, Engineer, Reviewer, …) talk to each other over a message bus, debate and bring you only the questions that block them. Use it to write a spec, debate a design, deliver a feature end to end with code review, run a security review or investigate an incident.
argument-hint: <template> <brief>   (feature-delivery | quick-delivery | bugfix | code-review | product-design | design-debate | security-review | incident-investigation)

The user asked to run a dynamic workflow: `$ARGUMENTS`

This command is the user's explicit request to run a workflow: you call the Workflow tool in step 3.

1. **Pick the template.** The first word of the arguments is the template id and the rest is the brief. If the first word is not a template id, run `${CLAUDE_PLUGIN_ROOT}/bin/dw --bus-server plugin_cdw_workflow-bus templates` and pick the template whose "for:" request types fit the brief; say in one line which one you picked.
2. **Prepare the run.** Run `${CLAUDE_PLUGIN_ROOT}/bin/dw --bus-server plugin_cdw_workflow-bus prepare <template> --brief '<brief>' --dry-run` (single-quote the brief and escape any single quote in it). When the user points at an existing document the team should start from — typically a spec for `feature-delivery` — add `--artifact <name>=<absolute path>` (e.g. `--artifact spec.md=/abs/path/spec.md`); the phase that would write that document is then skipped. The dry run compiles the workflow and prints the launch JSON without opening anything: `team`, `changesWorkspace`, `staffing` (members added beyond the template's team: `phase`, `member`, `agent`, the matched capability `tags`, `estimatedTokens`) and `optional` (capabilities a phase takes on only when the brief needs them: `phase`, `tag`, `description`, `active`).
   - If `optional` is present, decide from the brief which of those capabilities the work really touches, and only those; keep a one-line reason for each one you activate and each one you leave off. Run the dry run again with `--needs <phase>=<tag>[,<tag>...]` for them to see the resulting `staffing`.
   - If `staffing` is present, show the user who is added, to which phases and why (the matched tags, your reason for each capability you activated and the ones you left off) and the estimated tokens, and get their go-ahead before preparing the run; if they change the choice, use theirs.
   - Then run the same command without `--dry-run`. It compiles the saved workflow, opens the run on the bus and prints the JSON again with `runId`, `scriptPath`, `args`, `outputDir`, `watch`, `inbox` and `tail`.
   If `changesWorkspace` is true, the team will change files in this project (for `feature-delivery`: implement and commit on the current branch). Before launching, tell the user in one line which branch and that uncommitted changes of their own stay untouched.
3. **Launch.** Call the Workflow tool with `scriptPath` and `args` exactly as printed — `args` is a JSON object, not a string. If the tool rejects that combination, call it with `{name: <workflowName>, args}` instead (the saved workflow in `.claude/workflows`). The workflow runs in the background.
4. **Listen for the team.** Start the printed `watch` command with Bash `run_in_background: true`. It exits — and you get a notification — as soon as a message reaches `main`.
5. **Tell the user** in a few lines: the template, the run id, the team, where results land (`outputDir`, documents under `artifacts/`), and that they can follow the debate live with the printed `tail` command in another terminal.

When the watch task finishes:
- Read the messages: `${CLAUDE_PLUGIN_ROOT}/bin/dw --bus-server plugin_cdw_workflow-bus inbox --run <runId> --mark-read`. The bus tools never act as `main` (every agent of the run can call them): you read and answer for the user through `${CLAUDE_PLUGIN_ROOT}/bin/dw --bus-server plugin_cdw_workflow-bus`.
- A **question** (`expectsReply: true`) comes from the team's liaison and has already been debated: answer from this conversation only if the user already decided exactly that; otherwise show the user each question with its options and the team's recommendation, and wait for their answer. Then send it: `${CLAUDE_PLUGIN_ROOT}/bin/dw --bus-server plugin_cdw_workflow-bus reply <runId> <seq> '<answer, e.g. 1: a, 2: b>'`. The team is blocked until this reply arrives. To change the team's course, send a directive: `${CLAUDE_PLUGIN_ROOT}/bin/dw --bus-server plugin_cdw_workflow-bus send <runId> --to '*' '<directive>'`.
- **Relaying for the user.** You may analyse the user's request and send it on (a directive, or the answer to a question), but only what the user asked or decided. When you are not the user's own session (another agent passing the user's words on), add `--via <your name>` so the transcript shows who relayed.
- A **report** or anything else: summarise it for the user.
- While the workflow is still running, start the `watch` command again in the background.

When the Workflow task completes: summarise the result for the user (status, decisions, open issues, artifacts with their paths under `outputDir`, and for workflows that changed the project the `work` items with their status and changes and the `reviews` verdicts), stop any watch task still running, and offer to open the main artifact. Never answer a team question on the user's behalf unless they already decided it.
